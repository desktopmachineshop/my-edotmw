### D-010 · 2026-07-28 · Accepted
**Decision:** Unit stats live in `/units/*.tres` against the `UnitDef`
schema (`unit_def.gd`). Schema changes are versioned and recorded here,
not just in the code.

**Rationale:** Data-driven units are what makes the project directly
editable via Claude Code rather than requiring the Godot editor GUI, per
`CLAUDE.md`'s core premise. `UnitDef` now needs formation-shape and
morale-stat fields per D-019 from the start.

**Rejected alternatives:** Hardcoded per-unit-type script subclasses
(rejected — defeats the data-driven goal).

**Consequences:** New units are added by adding a `.tres` file, not by
writing new unit classes. Squad size (~40 soldiers per D-018) is a
`UnitDef` field, not a global constant, so it can vary per unit type if
needed later.

**Revisit trigger:** None currently.

**Schema log — SPLIT, one file per workstream (#366).**

The obligation is unchanged and is stated in the Decision above: a schema
change is **recorded, not just written in code**. What moved is only
WHERE — "here" is now one of the files in the table below.

The log used to live inline here, and by 2026-08-28 **six open PRs were
appending to it at once**. That is the exact shape `README.md` rule 1
forbids — *"never append to a shared file; two branches adding decisions
must be unable to conflict textually"* — and D-010 was the one decision
still breaking it, because its log is a running record rather than a
finished argument.

So the log is now one file per workstream. **D-010 itself keeps its ID
and its citations**; only the log moved (rule 4: historical IDs are
frozen, and code, tests and the justfile cite this one).

**Which file does my change go in? The WORKSTREAM's, not the schema's.**

A field added by naval is logged in the naval file even though it lives
on `UnitDef`. That looks wrong for about a second and is the whole point:
files exist to stop two branches touching one file, and branches are
organised by workstream. Splitting by schema instead would put naval,
techs and a plain unit-stat change back in `units` together, which is the
monolith with extra steps.

The cost, stated rather than discovered: **to see every change to one
schema you now read several files.** `grep -rn "UnitDef\." decisions/D-010-schema-*.md`
is the answer, and this table is what tells you which files exist to
grep. If a workstream ends and its file stops growing, leave it — a
closed log is a history, and merging it back would re-create the thing
this split removed.

**A new workstream adds a new file** rather than appending to somebody
else's, and adds a row here. That row is the only shared line, it is one
line, and an add/add conflict on it is a visible two-line merge rather
than a tangle inside a running log.

**Rules for an entry**, unchanged from when the log was inline:

- **Append at the end. Never reorder, never edit an entry in place** —
  the log is a history, and a rewritten entry is a history that lies.
- **Date it, name the field, give its type and default**, and say why the
  default is the safe one. `damage_vs_buildings` defaults to the SAFE end
  so an unaware `.tres` is conservative rather than catastrophic; that is
  the opposite of `bonus_vs`, whose missing-key default of 1.0 is right
  for a counter table and would have been exactly wrong there.
- **A field that is proposed and not built says so, loudly.** The techs
  log is entirely specification; anything reading it as a description of
  the repo would be misled.
- **This log records the SCHEMA, not the values.** A `.tres` tuning
  change is not a schema change and does not belong here — see
  `docs/status/` for the balance record.

- **2026-08-28 — added `MapConfig.preset: StringName = &""`.** Naval,
  #301, cut-list row 9. Which `/terrain` preset a map's ground is
  generated from. Empty — every map that shipped before this one — means
  "leave the settings' default alone", so `default`, `huge` and `ladder`
  are unchanged and a test asserts that rather than trusting it.

  `MapConfig`'s own header says terrain generation is out of scope and
  that its parameters "join this resource when they land". This is the
  smallest form of that and deliberately not the parameters: only WHICH
  preset, because **a map's identity and its terrain cannot be
  separated**, and the naval gate is what proved it.

  `maps/isles.tres` exists so an AI can be made to want a navy. Selected
  by dimensions alone it generated a **continents** world at isles
  dimensions — one landmass, `wants_navy = 0` correctly, and a gate that
  passes green having tested nothing. No recipe passes `--preset`, and
  `MapSettings.from_map` carried every other map field but not this one,
  so the map file was the only place the fact could live. D-076's lesson:
  a gate that cannot fire is a gate that lies.

  `--preset=` still overrides, because `server.gd` applies the override
  first and then resolves whatever `_settings.preset` ends up as.
