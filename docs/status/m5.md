**M5 (client scale) — the milestone D-015 called "LOD", renamed on
evidence.** Exit criteria are D-044; the work is D-045. M4's numbers made
"LOD" wrong in both directions: the simulation did not need it (the tick
budget was already met), and the client had never been measured at all.
So M5 measured the client first and built only what the numbers asked
for.

`just bench-render` is the new recipe — **native, because it needs a real
GPU**; `test-client`'s software rasteriser can say whether the picture is
correct but never how fast it is. It prints the video adapter, and **a
frame time without hardware attached is not a number anyone can use**,
the same rule as never quoting µs/squad without a squad count.

On Intel Iris Xe integrated, at 1,000 squads / 26,644 soldiers:

| | ms | fps |
|---|---|---|
| baseline | 94.50 | 10.6 |
| + terrain sampled from a precomputed field | 66.70 | 15.0 |
| + cull before derive (wrap-aware) | 56.06 | 17.8 |
| + render LOD | 35.66 | **28.0** |

500 squads now runs at ~57 fps. **The measurement overturned one of M5's
own criteria before it was written**: batching squads by unit type was
planned on the assumption of ~1,000 draw calls, and the real number was
154 — Godot already frustum-culls per-squad `MultiMeshInstance3D`s. The
frame was 97% CPU, all derivation, so batching would have solved nothing.
That is what taking a baseline first is for.

**Three rules carried out of it.** Terrain elevation is memoised
(`TerrainGen.elevation_field`) — sampling noise per soldier per frame was
the third instance of the same defect, after `distance()` per cell in
vision and `by_id` per produced squad. Culling on a torus must test the
**wrapped** copy (`TorusSpace.lattice_steps` is now the one definition,
shared with terrain tiling and camera wrap) or armies vanish at the seam.
And render LOD draws a distant squad **thinner, never smaller** — unit
size is tactical information a player reads off the screen.

**Watch `test-client`'s casualty gate.** It is meant to prove combat
happened and is now satisfied by *founding a town hall*, because
consuming the founding party reports through the casualty path. It passes
without any fighting. Recorded in D-045; fix it when next touching the
capture scenario.

**And "thinner, never smaller" was not enough on its own, because the
answer flickered (D-20260827-a-lod-tier-is-sticky, #155, 2026-08-27).**
Reported from a playtest as squads *semi* popping in and out **while
still in the player's camera** — part of a squad, in the middle of the
view, which is why it did not read as a culling fault. `_detail_for` was
a memoryless lookup on the current frame's distance, and the ladder's
steps are 40 -> 12 (**-70%**) and 12 -> 5 (**-58%**), so a squad sitting
anywhere near 55 or 110 world units flipped on the smallest movement of
itself or the camera.

The tier is sticky now: detail is LOST 15% past a boundary (63.25 /
126.5) and REGAINED at the plain one (55 / 110), with the side of the
band chosen by one remembered int per squad. Three things to carry:

- **A flickering representation is not a weaker one, it is no
  information at all.** D-045's rule is that unit size is tactical
  information a player reads off the screen; forty men one frame and
  twelve the next means force size cannot be read in the middle band of
  the view at all. That is what makes this a correctness fix rather than
  polish — and the same argument says a "never changes" hysteresis would
  be just as wrong, so the test walks a squad from 20 to 420 units out
  and requires it to pass through all three tiers in order.
- **The second trigger was an ARGMIN, and hysteresis alone would not
  have touched it.** Since entities are drawn at every visible copy the
  client picks one with `nearest_offset` — against what the camera LOOKS
  AT, while the ladder measured to where the camera IS. Two different
  points on this rig, so a tie between copies moved the distance a whole
  map period **with the camera still**: measured at height 40 on a
  100-unit period, 84.1 against 47.7, either side of 55. The fix is that
  the ladder reads a **minimum** over the visible copies, which is
  continuous across exactly that tie where an argmin is not — and it
  leaves `nearest_offset` alone for the callers that want a placement
  rather than a magnitude.
- **The ladder moved into `render_cull.gd` to be testable at all.**
  Every LOD check that existed was single-frame, and the defect is a
  frame-to-frame difference; `client.gd` needs a GPU (D-014), so a rule
  living there cannot be watched to fail. D-106's own amendment, applied
  again: when a rule cannot be tested where it lives, that is a fact
  about where it lives. `bench_render.gd`'s hand-copy of the three tier
  numbers went with it.

**What no still can show is the flicker itself**, so `test-client` and
`gen-model-preview` prove the squad-draw path still renders and nothing
more — the same split as the gatherer's chop CADENCE. The instrument for
this one is the owner's playtest.
